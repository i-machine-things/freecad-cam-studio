# Coding Best Practices & Reminders

> **Style rule:** Notes must be clear and concise — 300 characters or less each. Group by topic, not by date. Whenever a PR review (CodeRabbit or human) catches a mistake, add or amend a note here right away so it isn't repeated.

## FreeCAD CAM API accuracy

- FreeCAD CAM class names can be misleading by similarity, not just by absence. `Path/Op/Pocket.py`'s `ObjectPocket` is the **3D** Pocket op (`FeatureNoFinalDepth`, final depth not editable) — the 2.5D, shape-based Pocket with editable final depth is `Path/Op/PocketShape.py`. Verify against the actual pinned FreeCAD version's source (`raw.githubusercontent.com/FreeCAD/FreeCAD/<tag>/...`) before citing a class in spec/architecture docs — filename pattern-matching isn't enough.
- When adding a depth/geometry-affecting property via a documented hook like `_customDepthParams`, that hook may only feed the Z-level *iteration list* — the actual removal-shape *geometry* (`areaOpShapes`) can read the raw, unadjusted property directly and ignore it entirely. `AxialStockToLeave` shipped "verified" once by checking only `_customDepthParams`'s own return value — it silently did nothing to the real toolpath. Always verify a depth/geometry change against the actual generated `Path.Commands` Z values, never just the intermediate function that's supposed to feed them.
- When bounding a generated-geometry loop against a pathological input (e.g. a parametric sweep's sample count), capping only the *sample count* while leaving the underlying *continuous quantity* (e.g. total sweep angle) unbounded doesn't make the output coarser — it makes each remaining sample jump across a huge span, producing a degenerate/zigzag result, not a simplified one. Clamp the physical quantity itself first, then derive the sample count from the clamped value. Caught by CodeRabbit on the helix ramp's `MAX_RAMP_SEGMENTS` fix: capping segment count alone while `totalAngle` stayed astronomical for a tiny `MaxRampStepdown` produced thousand-radian per-segment jumps. "Didn't crash and finished fast" is not the same verification as "produced a geometrically sane path" — same family of mistake as the `AxialStockToLeave` note above.
- Before post-processing `obj.Path` after `super().execute(obj)`: `Base.execute` can return early without replacing `obj.Path` (no tool controller, bad base/stock). Set `self.commandlist = None` first and bail if it's still `None`, or you re-process your own previous output on every recompute.
- Before deferring a fix as "that geometry isn't available here", check what upstream leaves on the Proxy. `PocketShape.areaOpShapes` keeps the removal solids on `self.removalshapes` — enough to collision-check any added move (`_sweptAreaFits`). Two review findings sat deferred on a wrong assumption.
- Any move added to a toolpath (lead, ramp, link) must be checked against the pocket's walls/islands and rejected if it doesn't fit. "User must size it sensibly" is not a safety property. Include the radial stock to leave in the clearance.
- Modal X/Y: don't assume which command positions the tool. Stock output repeats X/Y on the descent rapid (`G0 X Y`, then `G0 X Y Z`); other paths omit it (`G0 X Y`, `G0 Z`). When moving a plunge point, retarget the whole run of rapids ending on it and assert no descent has XY motion.
- Only emit `F` when the feed is > 0. Stock output omits `F` for an unset tool-controller feed; an explicit `F0` on our added moves is inconsistent and a hard error on some controllers.

## Doc hygiene

- Never write `[[memory-link-name]]` syntax into actual repo documentation — that's Claude's own cross-memory-file link format, not valid prose or markdown for a human-facing doc. Caught one in `docs/ARCHITECTURE.md` referencing `[[project_freecad_fork]]`; should have been plain prose describing the fork.

## Fusion 360 CAM spec accuracy

- Before spec'ing an operation from forum posts/blogs, find Autodesk's own per-operation reference page (URL pattern `help.autodesk.com/cloudhelp/ENU/Fusion-CAM/files/GUID....htm`) — it's the authoritative, complete field-by-field list per tab. Forum-sourced research undercounted Pocket's Ramp Type options (5 found vs. 7 actually listed) and missed entire subsystems (finishing passes, feed optimization, tool orientation) that only show up on the reference page.

- When documenting a Fusion operation's parameter as "unique" to it, check the comparable operation's own reference page too. Autodesk often shares controls across dialogs (Pocket and Adaptive Clearing both expose axial/radial stock-to-leave) — don't infer uniqueness from only one op's doc page.
- Don't conflate adjacent-but-distinct machining terms when paraphrasing a parameter (e.g. Adaptive's "Optimal Load" is a max engagement/stepover limit, not "chip load" — a different, related quantity). Check Autodesk's own wording, don't substitute a closely-associated synonym.

## Cross-platform install paths

- Don't infer an app's per-OS config/data directory from a generic pattern or by analogy to other apps' conventions (e.g. assuming macOS mirrors `~/Library/Preferences/<App>`). Verify from the app's own docs or a runtime call — FreeCAD: `App.getUserAppDataDir()`. A wrong path is a silent no-op install, not an error.
- `~` does not expand inside double-quoted shell strings. Install docs with a quoted path containing spaces (e.g. macOS `"~/Library/Application Support/..."`) must use `"$HOME/Library/..."` instead, or the literal `~` gets passed through and the clone lands in the wrong place.

## Headless FreeCAD testing (offscreen flatpak)

- `Path.Main.Gui.Job.Create(base, template, openTaskPanel=True)`'s default auto-opens stock CAM's Stock-editing TaskPanel, which hangs indefinitely under `QT_QPA_PLATFORM=offscreen` (no real GL context — "No valid GL context found!" spam, process never returns). Our own commands that call this must pass `openTaskPanel=False` explicitly.
- Any headless test script run via `flatpak run --command=freecad --env=QT_QPA_PLATFORM=offscreen ... script.py` must wrap its whole body in `try/except/finally: os._exit(0)`. An uncaught exception mid-script does not exit the process — FreeCAD reports it and the GUI event loop keeps running forever instead, hanging the test.
- `Path.Op.Gui.Base.CommandResources.name` is not just a display label — `ViewProvider` also uses it as the lookup key into `Path.Op.Gui.Selection`'s per-op-type selection-mode registry (`PathSelection.select(self.OpName)`). A custom `name` raises `KeyError` at edit time. It must stay the exact upstream op-type string (e.g. `"Pocket Shape"`); put CAM Studio's own branding in `menuText`/`toolTip` instead, which have no such constraint.
- `Gui.UiLoader().createWidget("Gui::QuantitySpinBox")` only exposes `QAbstractSpinBox`'s base methods through the Python binding — `setValue()`/`value()`/`setDecimals()` raise `AttributeError`. Use the generic Qt property interface instead: `widget.setProperty("unit", "mm")`, `widget.setProperty("rawValue", x)`, `widget.property("rawValue")`.
- That widget's `"unit"` property only accepts FreeCAD's own "preferred display unit" for that Quantity *type* (get it via `quantity.getUserPreferred()[2]`, as stock CAM's own `PathGuiUtil.QuantitySpinBox` does) — an arbitrary string like `"mm/min"` is silently ignored, falling back to the app's configured preference (e.g. `"mm/s"` for Velocity), even though mm/min is the universal CNC feed-rate convention FreeCAD's own ToolController fields display. For a feed-rate field, don't fight this: use a plain `QDoubleSpinBox` with an explicit `" mm/min"` suffix and convert to/from the property's real internal unit (mm/s for `App::PropertySpeed`) yourself in getFields/setFields. Getting this wrong is a silent 60x unit error, not cosmetic.
- Flatpak FreeCAD has a private `/tmp`: a script path under host `/tmp` isn't visible inside the sandbox (fails with a misleading `SyntaxError ... <string>`). Keep test scripts under `$HOME`. In full-GUI mode `print()` goes to the Report view, not stdout — write results to a log file.
- A toolpath test oracle that samples positions along moves must not treat G2/G3 as straight chords — the chord midpoint of a corner arc sits inside the wall offset and reads as a false gouge. Always run a negative control (pre-fix code) to prove the oracle can fail.
- To screenshot a page, host it in a `QScrollArea` as the real task panel does. FreeCAD's theme dims disabled text only via `QScrollArea QWidget:disabled`; a bare top-level form shows disabled fields at full brightness and looks like a broken enable/disable. Assert `isEnabled()` too.
- Test under the unit schema the user actually runs (homeworkstation is ImperialDecimal, schema 3), not just metric. A hardcoded `mm/min` suffix sat beside inch fields unnoticed. Feed fields: per minute, length unit from `Quantity(1, Length).getUserPreferred()[2]`.
- Never write a `Gui::QuantitySpinBox` back with `if obj.X.Value != widget.rawValue`. The widget rounds to its display precision in the user's unit schema (3 mm reads back 2.999994 under inches), so any edit rewrote every quantity on the page. Record the readback at load and write only if it changed (`_qty_set`/`_qty_commit`).
- Drive widgets the way signals do in tests: call `page.getFields(obj)` after each click. A `.click()` on a still-disabled widget is silently ignored, which reads as a logic bug.
- A `QToolButton`/`QPushButton` label treats `&` as a shortcut marker ("Leads & Transitions" renders "Leads_Transitions"). Write `&&` for a literal ampersand.
- Opening an op's edit panel while its ViewProvider `deleteOnReject` is True (a newly created op) clears `Base` and refills it from the current selection. In a headless test with nothing selected, the op silently loses its geometry and the path is empty. Call `setDeleteObjectsOnReject(False)` to test editing an existing op.
- Our page can add bars to the upstream TaskPanel: it's the last page built, and its `initPage` sees `self.parent.featurePages`. `pages/pocket.py`'s `_attachBars` inits the extra pages itself and reorders the list in place.
- `QWidget.isHidden()` is True for a widget that has never been shown or parented, not only for one hidden with `hide()`. Don't use it to skip "unused" rows for widgets you just created; the Retract Height row silently vanished that way.
- Map FreeCAD heights to Fusion by what the generated G-code does, not by the names: the tool rapids to Safe Height and feeds from there (= Fusion Feed Height), and retracts to Clearance between passes. Start Depth is not where feeding starts.
- FreeCAD caches a Python view provider's methods when `ViewObject.Proxy` is assigned, and a newly assigned proxy is not `attach()`ed. To give an existing object our subclass, set `proxy.__class__ = Ours` on the attached instance, then re-assign `vobj.Proxy = proxy` to refresh the cache (`pages/setup.py` `adoptJob`).
- A toolbar command group's dropdown lives on the button (`toolbar.widgetForAction(a).menu()`), not on `QAction.menu()`.
- Before building a library/data system, check FreeCAD's own (Materials, tool library, setup sheets). CAM Studio built a parallel material library before finding FreeCAD's Machinability materials and Job Edit's (unlabelled) material button; it had to be replaced.
- FreeCAD's Materials Python API can't set a 2DArray value (`setPhysicalValue` with text silently stores nothing). Write the `.FCMat` YAML yourself -- 2DArray layout is a one-item list holding the rows -- then `MaterialManager().refresh()`.
- Materials in an add-on-registered *material* folder are invisible to vanilla FreeCAD (stock falls back to "Default"). Register only *models* from an add-on; save materials into FreeCAD's User library.
- Widgets you add to an upstream panel need a Python owner kept alive (e.g. an attribute on the panel). Qt holds bound-method slots weakly; an unreferenced helper object's buttons silently do nothing.
- FreeCAD runs an add-on's `Init.py` without `__file__`; locate the add-on through one of its packages. Don't name a package after a FreeCAD module differing only in case (`materials` vs `Materials`).
- `Gui.Control.activeDialog()` returns a plain `bool` (whether a dialog is active), not the dialog object — use `Gui.Control.activeTaskDialog()` for the object, and even that returns a C++-side wrapper, not the original Python `TaskPanelPage`/`TaskPanel` instance, so Python-only attributes like `featurePages` aren't reachable through it. To test a custom page's logic directly, instantiate the `TaskPanelOpPage` class yourself against the object instead of fetching it back through `Gui.Control`.
- `App::PropertyAngle` (and other Quantity-backed property types like `PropertyDistance`) returns a `FreeCAD.Units.Quantity` object from Python (repr `"3.0 deg"`), not a bare float — unlike `App::PropertyFloat` (e.g. stock `ZigZagAngle`), which returns a plain float. Passing a `Quantity` straight into `Gui::QuantitySpinBox.setProperty("rawValue", ...)` **silently fails** (no exception, widget just doesn't update) since Qt's property system can't convert it. Always use `.Value` explicitly when reading a Quantity-backed property into one of these widgets.
- When subclassing a `Path.Op.*.ObjectPocket`-style Proxy class (to add properties CAM Studio needs beyond stock CAM): check every overridden method in the upstream chain for `super(self.__class__, self)` (vs. the correct `super(ClassName, self)` or bare `super()`). `self.__class__` is OUR subclass and never changes across the recursive call, so it infinite-recurses two subclass-levels deep ("maximum recursion depth exceeded"). Found in `PathPocketShape.ObjectPocket.areaOpFeatures` — worked around by overriding that one method to call `PathPocketBase.ObjectPocket.areaOpFeatures(self, obj)` directly instead of inheriting the broken one-liner. Check for this pattern in every op module before subclassing it.
