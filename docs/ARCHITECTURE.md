# Architecture: build on FreeCAD's CAM module, don't reinvent it

Confirmed by reading FreeCAD's own upstream source (`FreeCAD/FreeCAD`, `src/Mod/CAM` — the module
was renamed from `Path` to `CAM` upstream; still imported as Python package `Path`internally).
No Autodesk code was involved in this inspection — this is FreeCAD's own, LGPL-licensed module.

## What already exists upstream (reused as-is, unmodified)

- **`Path.Main.Job.ObjectJob`** — the Job/Setup container: stock, WCS, model references,
  operation list. This is FreeCAD's equivalent of Fusion's Setup from
  `docs/spec/01-workflow-overview.md`.
- **`Path.Op.*`** — one FeaturePython proxy class per operation, each holding its parameters as
  ordinary FreeCAD properties (`obj.addProperty(...)`), with the actual toolpath geometry
  generated by the native `Path::Area` / libarea engine underneath:
  - `MillFace.ObjectFace` — Face
  - `PocketShape.ObjectPocket` — the 2.5D, shape-based Pocket (editable final depth) — this is
    the one Phase 1 wants. `PocketBase.ObjectPocket` is only the shared abstract base;
    `Pocket.ObjectPocket` is a different, *3D* Pocket operation that disables final-depth editing
    (`FeatureNoFinalDepth`) — don't confuse the two despite the similar class name (verified
    against FreeCAD 1.0.2's actual source, not just the file name).
  - `Profile.ObjectProfile` — Contour (FreeCAD calls this "Profile")
  - `Adaptive.PathAdaptive` — Adaptive Clearing
  - `Drilling.ObjectDrilling` — Drilling
  - (plus Helix, Slot, Deburr, Engrave, Surface, Waterline, Vcarve, ThreadMilling, Tapping,
    Probe, and more — out of scope until later phases per the roadmap)
- **`Path.Tool.*`** — tool/tool-library data model.
- **`Path.Base.SetupSheet`** — per-operation default parameter sheet (FreeCAD's analog to a
  template/preset system).
- **Post-processors** (`Path/Post`) — G-code generation. Reused unmodified.

The only GUI pieces that exist today are `Path/Op/Gui/*.py` (one `TaskPanel` class per operation,
e.g. `Pocket.py`, `Adaptive.py`, `Drilling.py`, `Profile.py`) and `Path/Main/Gui/Job.py` — these
are what this project replaces, and nothing else.

## Decision: ship as an external Addon, not a FreeCAD fork

- **No FreeCAD recompilation.** Everything above is pure Python (the native C++ parts — `Area`,
  the TSP solver, Voronoi — sit underneath `Path.Op.*` and are called by it; this project never
  touches them directly). An addon means no multi-hour C++ build pipeline, unlike
  [[project_freecad_fork]] territory (Allan's existing fork, where FreeCAD-core changes do need a
  real recompile/Flatpak build) — not needed for this UI-layer project.
- **File-format compatible with stock CAM.** This workbench creates/edits the exact same
  `Path::FeaturePython` objects stock CAM would. A document made in this workbench opens fine in
  vanilla FreeCAD CAM, and vice versa — we're not inventing a parallel data model.
- **Installable via FreeCAD's Addon Manager** like any other community workbench, once published.
- **Upstream CAM improvements (bug fixes, new ops) are inherited for free** — this project only
  ever adds a new Gui layer alongside the existing one, never patches `Path/Op/*.py` or
  `Path/Main/Job.py` in place.

## What Phase 1 actually builds

1. A new workbench entry (own toolbar/icon) so it runs alongside stock CAM without conflict.
2. New commands that create the same `Path.Main.Job.ObjectJob` / `Path.Op.*` objects stock CAM's
   commands create — same underlying objects, different command entry point.
3. New `TaskPanel` classes (new files, not edits to FreeCAD's own `Path/Op/Gui/*.py`) that present
   each operation's existing properties using the Setup → Operations tree structure and dialog
   organization described in `docs/spec/`, instead of stock CAM's own panel layout.

## Resolved: how the edit/double-click swap actually works

(Previously an open item — verified by reading `Path/Op/Gui/Base.py` and building/running a real
command against it.)

FreeCAD doesn't dispatch edit-on-double-click by object *type* through a central registry — it's
per-instance. Every `Path.Op.*` object's `obj.ViewObject.Proxy` is one *generic*
`Path.Op.Gui.Base.ViewProvider` class (the same class for every operation type), parameterized by
a small resource bundle (`Base.py`'s `CommandResources`) that names which `TaskPanelOpPage`
subclass to plug into the shared `TaskPanel` controller (`Base.py`'s generic `TaskPanel` class,
which assembles our op-specific page alongside shared pages like Base Geometry/Heights/Depths/
Tool Controller — those shared pages' own FreeCAD terminology already closely matches Fusion's
Heights tab, so they're reused as-is rather than rebuilt).

That `ViewObject.Proxy` assignment happens exactly once, at creation time, inside whichever
`Command.Create()` built the object (`Base.py`'s `Create(res)` function, called from
`CommandPathOp.Activated()`). We don't touch `Path/Op/Gui/*.py` at all — `commands/create_pocket.py`
builds its own `CommandResources` pointing `opPageClass` at `pages/pocket.py`'s own
`TaskPanelOpPage` (built from scratch in Python, no FreeCAD `.ui` resource reused) and registers
its own `Gui.addCommand(...)` entry. Objects our commands create open in our UI on double-click;
objects stock CAM's commands create keep opening in stock CAM's UI. Fully additive — no core
patch, no subclassing `ViewProvider` itself needed. See `pages/pocket.py` for the first concrete
example of this pattern (Fusion-style grouping/terminology, wired to the same underlying
`PocketShape.ObjectPocket` properties stock CAM's own panel edits).

**Not yet covered** (not required for Phase 1, flagged for later): making a *pre-existing*,
stock-CAM-created object open in our UI instead would require reassigning its `ViewObject.Proxy`
post-hoc (e.g. on document load) — not attempted yet, since Phase 1's plan is new jobs created
through our own commands, not re-skinning documents that already exist.
